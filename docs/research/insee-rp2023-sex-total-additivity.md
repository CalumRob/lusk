# Why RP 2023 `_T` age values can differ from `F + M`

**Finding:** In the cached INSEE file, the tiny discrepancies are in the source data itself, before this pipeline parses or sums anything. The CSV publishes population estimates with five decimal places; independently published `_T`, `F`, and `M` estimates can therefore fail exact additivity by one unit in the last published decimal (0.00001 person). The observed pattern is consistent with independently rounded estimates. INSEE’s public documentation reviewed here does **not** explicitly state that this is the reason these particular three series fail to add, so that causal explanation remains an inference, not a confirmed INSEE statement. There is no evidence here for confidentiality perturbation or a parsing defect.

## Reproduction against the cached source (read-only)

The producer manifest in [`pipeline/R/theme_demographie.R`](../../pipeline/R/theme_demographie.R#L49-L54) names the exact Melodi download as `DS_RP_POPULATION_PRINC_2023_CSV_FR.zip`; the cached extracted data inspected was `E:\Lusk\pipeline\data\raw\extracted\DS_RP_POPULATION_PRINC_2023_data.csv` (227,412,463 bytes). The file is semicolon-delimited, has columns `GEO; GEO_OBJECT; SEX; AGE; RP_MEASURE; FREQ; OBS_STATUS; TIME_PERIOD; OBS_VALUE`, and its rows are text. Values inspected directly include `F=73.79597`, `M=76.98426`, `_T=150.78022`, hence `_T - F - M = -0.00001` for GEO `01001`, `Y25T39`.

I parsed `OBS_VALUE` as decimal text (not binary floating point), selecting `GEO_OBJECT=COM`, `TIME_PERIOD=2023`, `OBS_STATUS=A`, the seven exhaustive age codes used by the producer (`Y_LT15`, `Y15T24`, `Y25T39`, `Y40T54`, `Y55T64`, `Y65T79`, `Y_GE80`), and each of `_T`, `F`, `M`. Across **244,006** complete commune × age triplets:

| `_T - F - M` | Triplets |
|---:|---:|
| 0.00000 | 195,838 |
| -0.00001 | 24,178 |
| +0.00001 | 23,990 |

No other difference occurred; the signed total is -0.00188 person across all these triplets. This is a symmetric one-last-digit pattern at published precision. The record values themselves already contain the difference, ruling out the pipeline’s subsequent aggregation as its origin. The finding is specifically about the cached CSV and these filters; it is not a claim that every geography/measure in the product behaves identically.

## What the official sources establish

1. **This is a weighted estimate, not necessarily an integer headcount.** INSEE’s documentation for the *exploitation principale* says that it covers all collected questionnaires, is exhaustive for communes below 10,000 residents and covers about 40% of dwellings in larger communes; observations have a “poids spécifique à l’exploitation principale” and people in the same dwelling share the dwelling’s weight. [INSEE, *Les exploitations principale et complémentaire*, PDF](https://www.insee.fr/fr/statistiques/fichier/2383177/fiche-exploitations_2024-06-27.pdf). The population-by-sex-and-age product is an exploitation-principale product (also stated by the source table citation on [INSEE’s RP2023 results page](https://www.insee.fr/fr/statistiques/8999105)).
2. **The displayed estimates need not be integers.** The source itself provides decimal `OBS_VALUE`s (five digits after the decimal in the checked records). The exact-product metadata CSV maps `SEX=F` to “Femme”, `M` to “Homme”, `_T` to “Total”; `RP_MEASURE=POP` to “Population”; and `OBS_STATUS=A` to “Normale”. These are category labels and status semantics, not a promise of additive values. The file also defines `K` as “Données inclues dans une autre catégorie” and `W` as “Inclut les données d’une autre catégorie”; the producer correctly filters status `A`.
3. **Sampling uncertainty is real but not the explanation for the arithmetic residue by itself.** INSEE’s precision note says: “Pour toutes les variables […] le sondage pratiqué entraîne une marge d’incertitude sur les résultats.” It explains that the uncertainty depends on commune type and the size of the variable. [INSEE, *La précision des résultats du recensement*, PDF](https://www.insee.fr/fr/statistiques/fichier/2383177/fiche-precision.pdf). This describes inferential precision (far larger than 0.00001 person); it does not say that the sex-total difference is caused by sampling, or specify the rounding/additivity procedure for these rows.
4. **RP2023 uses an adapted rolling-census method.** INSEE’s official population-reference methodology explains that the 2021 collection was postponed and methods adapted; for 10,000+ communes the estimate combines five survey years and calibrates to the housing register, while smaller communes use extrapolation/interpolation. [INSEE, *Téléchargement du fichier d’ensemble des populations en 2023*, methodology](https://www.insee.fr/fr/statistiques/8680726?sommaire=8681011). Those are overall population-reference methods; they should not be asserted as a specific explanation for a one-digit difference in this particular age/sex dataset.
5. **The exact file is the Melodi file endpoint recorded in the project’s producer manifest.** [Melodi file URL](https://api.insee.fr/melodi/file/DS_RP_POPULATION_PRINC/DS_RP_POPULATION_PRINC_2023_CSV_FR). INSEE says its data catalogue exposes definitions/modalities and downloadable CSV/Parquet and that Melodi provides access to data and metadata ([catalogue description](https://www.insee.fr/fr/information/8184173)). The cached metadata accompanying this download was checked locally as above. INSEE’s general legal notice says, “Sauf mention contraire,” public information and downloadable files are under Licence Ouverte 2.0, requiring attribution and no distortion/misleading interpretation ([INSEE legal notice](https://www.insee.fr/fr/information/2008466)).

## Interpretation and limits

- **Established:** the discrepancy exists as literal source values; it is exactly ±0.00001 in the checked records; values are published to five fractional decimal places; INSEE documents weighted principal-exploitation observations and sampling uncertainty.
- **Best-supported explanation, but still inference:** totals and sex components are separately estimated/published and rounded to five decimal places, so independently rounded values need not add at the last decimal. The balanced ±1-last-digit pattern is what this mechanism predicts.
- **Not established by reviewed INSEE documentation:** an explicit statement that `_T` was estimated/rounded independently from `F` and `M`, the exact rounding rule, or an official additivity guarantee (or explicit lack of one) for these rows. Do not present the inferred mechanism as an INSEE-confirmed methodological fact.
- **No indication of a parsing issue:** values are present in the raw textual CSV before pipeline reading; exact decimal arithmetic reproduces the delta. The pipeline reads the file via shared `lire_csv_long`, filters valid rows, then intentionally derives age totals as `F + M` in `pivoter_age` (see [`theme_demographie.R`](../../pipeline/R/theme_demographie.R#L182-L199) and [#L324-L330]).
- **No evidence that confidentiality caused this:** the checked product is aggregated population statistics, and the reviewed documentation describes sampling/weights and precision, not a confidentiality perturbation for these counts. This should be phrased as “no evidence found,” not proof that no disclosure control exists anywhere in production.

### Pipeline implication

The producer intentionally derives the seven age-band totals from `F + M` and does not use the source `_T` rows for those bands; its separate `_T`, `Y_LT20` value is an overlapping aggregate used for a different scalar. Replacing the derived totals with source `_T` would introduce a source-level last-digit non-additivity relative to the sex-specific values. This report establishes the nature and scale of that tradeoff; it does not make the product decision about regenerating outputs.
