# ADR-0038: Constrained common indicator serving contract

- **Status:** Proposed design for #590; schema and migrations require separately reviewed implementation tickets.
- **Parent:** ADR-0033; refines the serving-shape direction in ADR-0035.
- **Authority:** product owner owns catalogue membership, labels and user-visible semantics. R/Parquet owns computed facts and pipeline metadata. This ADR does not approve production DDL.

## Decision

Adopt three shared numeric observation grains—scalar, declared detail/profile, and ordered series/state—plus a narrowly justified structured-evidence grain for observations whose coordinates are semantic rather than an ordinary indicator axis. Use constrained descriptor rows to declare each dataset's shape and axes; do not make a generic nullable-column EAV store or one table per indicator. Common tables are shared across themes, and each physical table is independently versioned. Descriptors and provenance that determine a table's meaning are published in the same atomic table snapshot (or an explicitly declared dependent-table transaction).

All observations are keyed by a stable `indicator_id` (dataset/indicator identity, not display label), a validated territory identity/type, and shape-specific axes. A descriptor has a stable key, shape enum, declared eligible level set, public label, unit (including stored-value scale), direction (`high`, `low`, or `none`), comparison facet (nullable only when no comparison is defined), and declared axes, order, completeness and denominator semantics. Reject unsupported shape/axis combinations; API never accepts arbitrary columns or invents descriptors. A descriptor version participates in the serving table content version. Descriptor/source disagreement or unknown indicator keys fails publication rather than being inferred from values.

### Physical shape contracts

1. **Scalar observation**: one row per publication × indicator × territory. A scalar may be a measured value or an explicitly unavailable value with a typed reason (e.g. suppressed/unsupported); no row means not published/not eligible, not zero. Zero is a measured value. Do not encode unavailable as a magic number. Nullable numeric value is permitted only with a constrained status/reason pair. Support/denominator counts are separate typed fields, not inferred from a displayed unit. Comparison facet must resolve to this indicator or a separately declared scalar facet.
2. **Declared detail/profile**: one row per publication × indicator × territory × declared detail key × optional declared second axis. Descriptor declares closed axis universes, labels and order, per-detail unit, denominator rule, and either `dense_complete` or `sparse`. Dense profiles publish every allowed coordinate (including explicit unavailable statuses); missing coordinates invalidate the snapshot. Sparse observations publish only observed coordinates; omission means no evidence, never zero/false. Comparison is by declared scalar facet or a specifically declared detail, never a sum inferred by SQL.
3. **Ordered series/state**: one row per publication × indicator × territory × declared axis point/role. Descriptor declares axis kind, ordered axis values and whether points are expected complete or may be absent. Preserve missing point status instead of interpolating. Observation period, source vintage, source publication date and database published-at are distinct. A pooled/current headline is a scalar descriptor, not silently a series endpoint. State roles (e.g. initial/final) are typed roles, not year aliases.
4. **Structured evidence (dedicated constrained family only)**: use only for non-indicator evidence with genuine multi-coordinate grain that cannot be represented honestly as declared profile or series. Coordinates are shape-specific and closed by a versioned descriptor; payload-specific axes cannot be free-form. Denominators, count units, completeness, absence state and source lineage are explicit. API exposes named read methods for the bounded evidence family, never a generic row query. Programme membership in particular is a sparse relation: an absent row is not false. If review establishes it's a simple declared category profile, it can instead use the detail grain.

Every observation carries provenance references to one or more source dataset/vintage records, with observation-level associations where vintage varies by point. Provenance records distinguish dataset identity from vintage. Count, denominator, support/suppression, and completeness semantics are declared, not guessed. A source-backed zero is retained; null is not zero; absent territory/axis is not a null observation. API reads take one repeatable-read snapshot and return the relevant independent table versions/token. A publisher validates key uniqueness, descriptor membership/order, allowed territory levels, dense completeness or sparse policy, null/status constraints, denominators, provenance references and row parity with canonical Parquet before atomically replacing facts and content marker. Failed publication leaves the last full version readable; an absent/stale required marker yields unavailable, not mixed versions.

## Existing pilot mapping and disposition

- `essential_service_access`: keep the current physical table during migration. If owner selects uniform shared scalar storage, replace it only after a new publisher/reader is proven and one-to-one identity mapping is validated. The fifteen service-mode keys remain individually identified; if using detail coordinates, each tuple must map bijectively to its original key and retain label, source, direction, eligibility, unit/scale, facet and missingness. Preserve existing response/behavior: nullable share versus zero, source lineage, scope metadata, per-service/mode medians, car/foot gap and bike/foot gain, rank ties, comparable counts, supported territory levels and unavailable states. The denominator/reference semantics required by those reads must be represented; do not call a share a count or reweight it. Existing product comparison controls and API response remain compatibility contracts under #587, not a migration-time owner re-decision.
- `building_ramp`: retain current physical table unless implementation demonstrates concrete schema improvement. A replacement is justified only if it actually adopts shared descriptor/provenance/publication infrastructure and validated axis contracts—not merely a renamed table. Its eleven quantile-position ordinates by territory and mode, own `total_buildings`, source and direction form a curve/evidence grain; encoding as an unqualified generic list/detail would hide curve and weighting semantics. R-published per-commune points remain authoritative. Preserve ADR-0036: building-count-weighted mean of corresponding commune points, not pooled quantiles; at least two available members, distinct commune expansion, no automatic focal inclusion, absent member contributes no buildings. Fractional peer values are valid.
- `building_grid`: retain current physical table unless a concrete schema improvement justifies replacement. Any replacement must share descriptor/provenance/publication infrastructure and validate its axes, rather than simply rename it. Its mode and 30 declared breadth/depth coordinates, cell counts and own building denominator form a grid evidence grain. Group comparison pools counts and recomputes cell shares; it is not the ramp mean. Replace the explicit absent sentinel with a typed availability status only as part of a parity-proven reader migration. The grid is in scope and remains a consumer; retirement requires a separate product decision.

The shared infrastructure is the uniformity target: independently versioned publications, validated descriptors, provenance/source-vintage links, and shape-completeness checks. The pilot observations remain different in grain. Keep their tables initially; replacing them is optional and must demonstrate a concrete improvement beyond renaming. The building ramp and grid retain different evidence invariants. Existing URLs/response fields/availability and metric labels remain compatibility contracts through cutover. Service-registry metadata may become descriptor-owned allowed service axes only after exact parity; it must not cause hidden “all combinations are zero” completion.

## Bounded API and publication identity

API surface remains typed and request-bounded: `readScalarComparison(indicator, territory, declaredScope)`, `readDeclaredProfile(territory, indicator)`, `readSeriesOrState(territory, indicator)`, and named evidence readers for services/building ramp/grid/programme membership. Callers cannot provide raw SQL, arbitrary axes or unsupported levels. Comparison results identify actual resolved peer scope, metric, comparable count, focal value and relevant table-version token; no fixed-scope `rang_*` feeds new computations. API never recomputes R transformations, indicators, aggregation/suppression, ratios or source eligibility. If cross-table joins are needed, read markers and facts within one committed transaction and fail closed if required descriptor/reference versions are incompatible.

Publication uses explicit opt-in R targets after canonical Parquet and required shared references. Each table has its own content version covering values and meaning-affecting descriptors/provenance. A transaction can replace related tables and markers together; no global release marker, no re-write of unchanged tables, and retry compares DB marker to local canonical version. Fresh-install schema is updated explicitly; existing installations receive numbered additive migrations. API readers switch only after the new full table passes parity and availability checks.

## Expand–migrate–contract sequence

No big bang. Every stage preserves current reads:

1. **Expand:** create constrained new tables/markers only where the agreed design actually needs them, publisher validators, API reader implementations and dual-read/parity tests in an additive numbered migration; do not remove old tables/endpoints or alter existing readers. Fresh-install `schema.sql` describes end state; migration scripts upgrade existing DB without assuming empty tables. Publish new projection independently.
2. **Validate:** compare canonical Parquet row/key/value/status/provenance/denominator sets and endpoint payloads against old reader for all levels/scopes, including unavailable/zero/absent and overlapping building selections. Run API contract + disposable-Postgres transactional rollback/failure tests, representative-size Pi latency/storage/backup checks per #587 before switching. Any mismatch leaves old reader active; failed publish keeps previous version.
3. **Migrate one consumer:** behind an explicit, reversible server-side route/reader switch, serve new facts only when their complete marker and descriptor token exist. Keep old storage populated/readable during soak; do not silently fall back to static JSON. Roll back route to old complete tables if errors/parity/latency fail.
4. **Contract:** only after production monitoring/recovery readiness and all consumer/read-model/reference searches show no dependency, remove old table/functions/indexes and old read path via a separately reviewed guarded migration. Rehearse rollback and dependency checks; no CASCADE. Static structured artifact removal remains per artifact and only after every named consumer has migrated/retired, including read-model and map consumers. Unmigrated static pages remain correct; a migrated API page fails visibly/retryably when unavailable, not stale-static.

### `dataset_publication` retirement

The historical `dataset_publication` row is not the new publication identity. Do not drop it in this design or while legacy `api/importer.py` / tests use it. First adapt or remove the legacy Python database-write/import path and its historical schema tests in a separately reviewed change; preserve pure validation only if a named consumer remains, and prove no runtime/deploy/CI references. Then inspect live catalog dependencies (foreign keys, views, triggers, functions, grants, owners and external operational references), back up and verify current readers use only `table_publication`. A numbered additive guarded migration must assert expected database/schema and expected relation/columns, refuse unknown dependents/state, run transactionally with lock timeout, and drop only the retired object explicitly—never `CASCADE`. Preserve no historical row as an active marker; document rollback as restore/recreate from backup, since dropping history is not reversible by down-migration. No live DDL is authorized by #590.

## Follow-up implementation tickets and ordering

Recommended wave; tickets can be independently owned where dependency allows:

1. **Schema/publication foundation**: shared descriptor, source-vintage links, scalar/detail/series tables, version markers, fresh-install schema + additive migration + publisher validation. Depends on owner agreement on descriptor and null/status contract; not blocked by #582 and need not wait for a catalogue survivor list.
2. **Service-read representation decision and tracer**: owner chooses recommended shared scalar rows plus grouped API projection, or bijectively mapped constrained detail coordinates. Preserve each service-mode `indicator_id` and existing response semantics; switch only after canonical and old/new API parity. Depends on foundation, not search.
3. **Building evidence review/cutover**: retain ramp/grid physical tables initially. Implement shared descriptor/provenance/publication integration; separately replace a pilot table only if it produces an actual schema improvement. Preserve ADR-0036 behavior; independent from scalar/profile cutovers.
4. **Representative active indicator slices**: scalar comparison first, then profile, series and multi-vintage state as independently scoped consumer tickets; each selects only the facts its named consumer needs and proves canonical R fixture parity. Sparse grants/membership gets a dedicated follow-up after deciding detail vs relation contract.
5. **Source/freshness metadata and static consumers**: migrate Sources and metadata/run-report only after field-level consumers/contract review; retire static files individually after full reference audit and recovery readiness.
6. **Legacy importer and publication-table cleanup**: remove/adapt importer and historical tests; guarded `dataset_publication` retirement only after all dependencies are removed and operator preflight approves. This is cleanup, not prerequisite to the common schema.

#582 global search remains a sibling decision about its static bootstrap/read path and measured performance; it is not a schema prerequisite or blocker for any indicator shape. #589 inventory is merged and is the evidence baseline. Owner decision to escalate before service implementation: shared scalar rows grouped by API (recommended) versus a constrained detail encoding with a validated one-to-one mapping to each of the fifteen existing `indicator_id`s. Other per-slice decisions: dense/sparse declaration and typed unavailable reasons, exact source fields needed on Sources, and whether programme membership is relation-specific evidence or a sparse declared category profile. These are not blockers to the foundational schema absent a dependent indicator selection. Existing service comparison behavior and Variant E ramp/grid reads are compatibility requirements, not choices to reopen; any future product retirement/change requires its own decision.

## Rejected alternatives

- One universal key/detail/value table with many nullable fields: cannot enforce independent axes, completeness, denominators and evidence semantics at row level.
- Table per indicator or per theme: duplicates schema/publisher/API code and couples physical schema to catalogue churn.
- Replace pilot tables merely for naming uniformity: unless descriptor/provenance/publication contracts or meaningful validation improve, keeping the already-serving physical grain is cleaner and safer.
- Big-bang replacement, static/API dual-serving indefinitely, or SQL-side computation: breaks continuous correctness, creates split freshness ownership, or moves R's authority into the serving layer.
- Drop `dataset_publication` merely because no live FK is visible: importer/tests and non-catalog dependencies must first be removed and explicitly checked.
