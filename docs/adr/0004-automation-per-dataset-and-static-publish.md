# The automation runs per-dataset, publishes to `public/data/`, and notifies only when it needs the human

Issue #7 scoped the automation follow-up: a GitHub Actions weekly cron running `run_pipeline()`, plus the `publish(backend = "static")` seam stubbed in issue #6 (ADR-0003). Grilling (2026-08-03) surfaced two facts that force the shape: (1) **GitHub Actions cannot handle every dataset** — OSM extracts (`bretagne-latest.osm.pbf`, ~311 MB), OCS GE GeoPackages (~1.5 Go/dép), BDNB (~700–950 MB/dép) are too big, need desktop tooling, or need an API key; the Démographie manifest's four INSEE files (all keyless HTTP downloads, verified live) are cron-able today. (2) The payload needs a **committed home**, and `pipeline/data/` is gitignored by design ("données téléchargées et produites — jamais versionnées").

**Decision (user, 2026-08-03):**

- **Per-dataset automation mode.** The source manifest gains a `mode` column with values `cron` (the runner downloads it directly — small, keyless HTTP files) and `manuel` (too big / needs desktop tooling / an API key). In cron mode, `download_sources()` fetches `cron` sources, **skips `manuel` sources without failing**, and records a per-dataset status. Local full runs keep today's behavior: download everything, stop loudly on failure.
- **Cron failure behavior.** A `cron` source that fails after the existing retries is recorded as `échec` in the run report, the report is committed (traceable), the run stops loudly (exit non-zero → GitHub natively flags the run), and the notification step opens/updates the alert issue. A partial run is meaningless for Démographie (all sources feed the compute), so it stops rather than publishing a degraded payload.
- **Run report.** A per-run record committed alongside the payload: per dataset, `status` (`cron → frais/échec`, `manuel → à traiter à la main`) + timestamp. The durable trace of a run and the input to the notification seam.
- **Notification seam — not the rule.** The workflow opens/updates a GitHub issue **only on action-needed**: cron `échec` today. The "manuel-overdue" rule is a documented stub — "overdue" for OSM (daily) and BDNB (yearly) are different questions, and no manuel source is in any manifest yet; the rule is defined per-source the day one appears. The report lists every manuel source as "à traiter à la main" automatically, so the data-driven structure needs no change then.
- **Payload home: `public/data/` at the repo root.** One line opens `!/public/` in the root `.gitignore` (written to be opened — "future code pushes without editing this file"). Pages serves it at a clean URL; the future Vue app fetches it relatively; parquet + JSON + run report + vintages all live there. The payload is the product's artifact, not the pipeline's internal cache.
- **Diff-and-skip commit.** The workflow builds, diffs the fresh payload against the committed `public/data/`, and commits only when something changed — otherwise "nothing to publish". No empty weekly commits, no Pages redeploys for identical data. A fresh checkout has no `data/raw` cache (gitignored), so every run re-downloads the ~85 MB and rebuilds; the diff is what keeps history meaningful.
- **JSON as a tested serialisation, parquet canonical.** `publish(backend = "static")` writes the three tables as parquet (the canonical, downloadable open-data artifact) **and** table-level JSON projections (what the app fetches), both generated from the same in-memory tables, with a test asserting the JSON parses back to exactly the parquet tables — drift is impossible, not just unlikely. Per-territoire fiche files are rejected (a second shape to keep in sync, 1 269 files of git noise, and the app joins client-side per `docs/architecture.md` §Application).
- **No source/provider registry.** A per-provider table (name, publisher, URL, last run, reachability) was considered and rejected: git history and CI logs already record "last run"; the download step already fails loudly on an unreachable source; "last update" is per-dataset, not per-provider. A 2-row registry with no consumer is exactly the "structure without a consumer" smell ADR-0003 was written to avoid.

**Considered options:** (1) a source registry with tracked per-provider status — rejected, no consumer, drifts (see above); (2) issue on every run — rejected, the report is the durable trace and weekly issue spam is noise; (3) commit every run unconditionally — rejected, manufactured empty commits and a freshness line that is theatre; (4) per-territoire fiche JSONs — rejected, second shape + git noise; (5) browser reads parquet directly (`hyparquet`) — deferred: the app is the biggest unknown in the product, JSON's `fetch().json()` is native and zero-dependency, and the equality test kills the drift argument; revisiting is a publish-config change, not a contract change; (6) build the manuel-overdue cadence rule now — rejected, dormant logic inventing semantics for sources not yet in any manifest.

**Consequences:** idempotence becomes visible instead of documented (diff-and-skip); the "alive" freshness claim is honest — a real INSEE release changes the payload and commits; Habitat and Économie/Emploi replicate the per-theme trio (manifest + indicators + vintages) and inherit the cron/manuel split for free (DVF cron, BDNB/OCS GE manuel); the workflow needs `contents: write` permission and a `workflow_dispatch` trigger alongside the cron (run-it-now the day INSEE publishes); the vintage table is untouched — still the watchdog seam. Supabase remains a documented seam (`publish(backend = "supabase")`), unchanged.

> ## Amendment 2026-08-12 — the cron's build step runs the targets graph (#329/#343); the store is not cached between runs (deferred to #338)
>
> **The change (issue #343 — the cron wiring of the targets port #329).** The weekly workflow's build step no longer calls `run_pipeline()`: it runs the targets GRAPH (`targets::tar_make()`), with the run configuration set explicitly (`LUSK_MODE=cron`, `LUSK_CACHE=data/raw`, `LUSK_SORTIE=../public/data`, and `LUSK_THEMES = "demographie,habitat,economie"` — the THREE LIGHT themes, amended 2026-08-14). The full six-theme run (the five descriptors + the shared Programmes payload, ADR-0013) REMAINS the graph's contract — proved byte-identical by the unchanged test — and becomes the cron when #338 (the store cache) and the runner's download budget allow: today a cold full run is multi-hour and downloads ALL Milieux sources including the ~7 GB OCS-GE archives, and Mobilité is the flagship slow-clock rebuild; the shared Programmes payload stays full-run-only (unpublished by the cron, same as the pre-graph Démographie-only cron). The download-failure report fallback in the build step mirrors the restriction: it re-runs `download_sources` over the three light themes' manifests only, so a failure report never lists sources the run never attempted. The cron-mode semantics are PRESERVED: the graph passes the mode through to `download_sources()` unchanged — `cron` sources are downloaded, `manuel` sources are skipped without failing and recorded "à traiter à la main", and a cron source failing after the retries is recorded "échec" then the run stops loudly. The #8/#10 report semantics are preserved too: the run report is a target INDEPENDENT of the downstream steps (tar_cue always, error = "continue") — written even when a target fails. The loud stop is carried by the build step: `tar_errored()` non-empty makes the run red (non-zero exit → the "Signaler l'échec du build" step), and the trace (the report, committed by the commit/skip decision) is committed as before. When the DOWNLOAD itself fails, the DAG writes no report (the report targets depend on the sources): the build step then writes the failure report itself (the "échec" statuts carried by the error, issue #8) — the cron-wiring step's responsibility, documented in `_targets.R`.
>
> **Cold rebuild assumed.** The `_targets/` store (gitignored) is NOT cached between runner runs: every cron run re-downloads and rebuilds the three light themes it covers — the cost of today (the same run class as `run_pipeline()` on an empty cache). The store-cache decision (runner Actions cache, #338) is DEFERRED: it will live when the cron becomes production; nothing changes here. The graph's surgical regeneration (Q1–Q3) remains the port's value for LOCAL runs.
>
> **Consequences.** The workflow (`.github/workflows/pipeline-cron.yml`) carries the run configuration as environment variables on the build step; `run_pipeline()` stays the UNCHANGED oracle (proved byte-identical by `test-targets-byte-identical.R`); the commit/skip decision, the alert seam and the tests-first order are unchanged. ADR-0008 is NOT amended: the graph's geometry target (`geometrie`) behaves like `run_pipeline()`'s `publier_geometrie()` call — the shared artifact, published to the same target.
