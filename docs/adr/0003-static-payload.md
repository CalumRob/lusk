# v1 serves a static payload — the pipeline is the database; Supabase is deferred until a feature needs a backend

The original architecture pointed at **Supabase** as the v1 storage: "the pipeline publishes the fiche payload to Supabase", "Supabase schema = the payload shape", the app queries it at runtime. The reality of the payload made that a solution in search of a problem: the full Démographie payload (all 1 269 territoires) is **~170 KB of parquet** (indicateurs 155 KB · histoires 15 KB · vintages 1 KB); a full four-theme v1 is on the order of 1–4 MB. More importantly, the product does **no ad-hoc querying** — the pipeline precomputes every indicator, rank, story, and vintage stamp at refresh time, and the app renders a projection of a payload it already holds. A lookup over a few MB in the browser is instant; a database adds provisioning, secrets, a runtime dependency, and a paid-ish third party without adding a capability. The only planned feature that genuinely needs a backend is the **AI query layer**, which is explicitly deferred (`docs/scope.md`) and, when it arrives, is a *separate service* — not the fiche backend.

**Decision (user, 2026-08-03):** v1 is **static-first**. The pipeline publishes the payload as static assets on the same host as the app; the app fetches them at runtime; the browser is the query engine; Supabase is deferred until a feature needs it. Concretely:

- The existing `publish(payload, target, backend)` seam gains `backend = "static"` — a new value next to `"parquet"` and the future `"supabase"` — writing the canonical **parquet** (the open-data artifact, downloadable for the data-manager peer) plus **JSON projections** (what the Vue app actually fetches).
- The GitHub Actions cron (issue #7) runs `run_pipeline()` → `publish(backend = "static")` → commits the fresh files → GitHub Pages (or any static host) serves both the app bundle and the data. Refresh = new files with new dates; the app code does not change.
- **The "alive" claim becomes true the moment the cron runs** — the freshness line on the landing reflects real file dates, which is the honest version of the promise and the brand.
- The **vintage table is untouched** — still the watchdog seam, unchanged (`docs/architecture.md` §Storage).

**Considered options:** (1) Supabase now — rejected: a database for a payload that fits in a few MB; adds provisioning, secrets wiring, a runtime dependency and the "alive" promise hanging on a third-party service, all to serve lookups the browser can do natively; nothing in v1 queries arbitrarily; (2) embed the payload in the app bundle at build time — rejected: refresh would mean rebuilding the app; static files fetched at runtime decouple data refresh from code deploy; (3) serve the payload statically from the app's host, parquet + JSON — **chosen**.

**Consequences:** issue #7's blocker ("user provides Supabase project + keys") disappears — the workflow is checkout → `renv::restore` → tests → build → deploy, all GitHub-native, no secrets in the repo. The "Supabase keys live in the deployment environment" line in `docs/principles.md` §5 remains as a promise *for when* a backend exists, not a v1 dependency. Nothing is foreclosed: the payload contract stays the seam, and `publish(backend = "supabase")` remains a mechanical follow-up (per the original issue #6 spec) the day a feature needs it. France-wide coverage later would want file splitting (per-theme / per-département), not a database — ~35 000 communes is still static-hostable. The README's automation language and the freshness promise are now literally true rather than aspirational.
