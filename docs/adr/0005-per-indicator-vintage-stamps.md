# Each indicator carries its reference source's vintage — not a theme-level buffer

The payload contract (`docs/architecture.md` §The fiche payload) declares **two vintage dates per indicator**: `vintage_date_reference` and `vintage_date_publication`, columns on the `indicateurs` table. The code did not honour the contract: `run_pipeline()` stamped *every* indicator row with the `serie_historique` vintage — the "tampon de fraîcheur du thème" — even though `structure_age` is computed from `age_detail` (PRINC) and `taille_menages` from `menages`. Today this is harmless (all three RP files share 2023 / 2026-06-30), but the `vintage_source` *name* is wrong for two of the four indicators — every row claims "INSEE — Série historique du recensement". The moment the sources' release dates diverge, the stamp would lie.

**Decision (user, 2026-08-03):** per-indicator vintage stamping.

- **`INDICATEURS_<theme>`** — a per-theme table declaring each indicator: `key`, `libellé`, `sources` (the source ids it draws on), `source_reference` (its freshness authority), and its expected multiplicity. This replaces the hardcoded key list in `validate_payload()`.
- **The reference source is declared, not inferred.** Each indicator row names its reference source explicitly, maintained like the manifest. The documented rule for choosing it: *the source contributing the indicator's **signature component** — the thing that makes the indicator what it is; never a shared denominator.* Applied today: `structure_age` → `age_detail` (the age tranches are the signature; the population denominator is shared plumbing), `densite`/`evolution_1968` → `serie_historique`, `taille_menages` → `menages`. Single-source indicators are trivially that source.
- **Stamping.** `assembler_indicateurs()` joins each indicator's reference source to the vintages table (already built) and stamps each row from it — `structure_age` carries PRINC's name and dates, `taille_menages` carries ménages', etc. The theme-level buffer dies.
- **Enforcement.** `validate_payload()` gains: every key in the payload exists in `INDICATEURS_<theme>`, and every stamped vintage equals its declared reference source's. A run that adds an indicator without a row, or stamps from the wrong source, fails loudly. The table is the contract; "à propos" only has to *display* the rule, never enforce it.

**Considered options:** (1) keep the theme-level buffer — rejected: the contract already says per-indicator, the app isn't built (migration cost is zero now, real later), and new themes copy the skeleton so retro-fits would multiply; (2) stalest-input rule (stamp with the oldest `date_publication` among an indicator's sources) — rejected: an indicator's stamp flips when a *secondary* input updates, noisy and hard to reason about; the reference-source rule is stable and matches how the domain thinks; (3) infer the reference source by rule (most columns, first-listed…) — rejected: fragile and opaque; declared data, like the manifest, is deterministic and human-maintainable.

**Consequences:** the payload is honest at source level — each indicator's freshness line names the source it actually came from; the app renders per-indicator vintages (the "alive" promise is true per indicator, not per theme); Habitat and Économie/Emploi replicate the table when they build; the `histoires` table is untouched (its Story is single-source, `serie_historique`, and the product treats the Story's vintage as part of the theme); the vintages table is unchanged and remains the watchdog seam.
