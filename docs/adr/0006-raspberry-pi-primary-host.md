## The # v1 serves from a home Raspberry Pi — primary host, repo as source of truth, pre-warmed Vercel as failover and dev environment

ADR-0003 settled static-first: the pipeline publishes the payload as static assets on the same host as the app, and ADR-0004 made the GitHub Actions cron the publisher, committing fresh files that "GitHub Pages (or any static host)" serves. What "the host" actually is stayed open — Pages was the default, Vercel was available (the user hosts another dashboard there), and a home Raspberry Pi was described as "a possible future watchdog, never the workhorse". The user's motivation is **sovereignty/control**: the payload is theirs, served from their own box, no third-party free tier — the same reasoning that runs AdGuard locally rather than on a cloud DNS. Their Pi (a 4, on 24/7) already runs AdGuard and cloudflared (a couple of Stremio addons), so the security-critical piece — the tunnel — is already in production on that box.

The facts that made it safe: the Démographie payload is ~0.2 MB of parquet (1 269 territoires), 1–4 MB projected for full v1; the working set fits in the Pi's page cache, so the SD card is not on the request path (SD wear is a write problem, and a read-mostly host barely writes — OS logs redirect to tmpfs). The visitor-facing ceiling is the home upload bandwidth, not the hardware. And the user's "I'll notice if it drops" claim is credible because the family's DNS runs on the same box: a connectivity loss kills AdGuard, which the household notices within minutes.

**Decision (user, 2026-08-03):** v1's primary host is the home Raspberry Pi, served through the existing cloudflared tunnel. Concretely:

- **The Pi is the primary host; there is no automatic mirror.** The tunnel points at the Pi's nginx; no open ports; TLS terminated at the tunnel edge. GitHub Pages is dropped as the default. The failover is a **pre-warmed Vercel project**: connected to the repo, auto-building on push, routed to nothing in normal operation; the day the Pi dies, the user flips the routing (minutes, DNS/TTL caveats aside). Nothing serves from Vercel until that flip — it is not a mirror. Vercel doubles as the **dev/preview environment**: PR previews and push-to-main deploys live there, so no development ever happens on the Pi.
- **The repo is the source of truth; the Pi is pull-only.** A systemd timer runs `git pull` every 30–60 minutes; the Pi serves `dist/` + `public/data/` from the working tree. The Pi never builds, computes, or pushes — it is disposable: SD death means re-provisioning by re-cloning. The cron and the tag build keep publishing to the repo exactly as before; "the Pi pulls" replaces "Pages redeploys" as the last hop.
- **Releases are tag-gated; data is not.** Push to main → Vercel only; the Pi does not move. A git tag → Actions builds `dist/` and commits it → the Pi picks it up on the next pull. Data (the weekly cron commits to `public/data/`) flows on its own schedule through the same pull. One pull channel, two rhythms: code moves deliberately, data moves automatically.
- **Docker on the Pi is runtime, never a release mechanism.** The Pi runs nginx-alpine via docker compose, matching how AdGuard/cloudflared run on the box. Docker images are *not* deployment units for Lusk's content: baking data or dist into an image would make every refresh a rebuild + redeploy — the coupling ADR-0003 rejected. Watchtower has nothing to do for Lusk: the image is static.

**Considered options:** (1) GitHub Pages or Vercel as the default host — rejected: the user's motivation is sovereignty, and the Pi is already on 24/7 with the tunnel infrastructure in place; (2) an automatic Pages mirror alongside the Pi — rejected: the user prefers to react manually, and the AdGuard canary makes that credible; (3) a Docker image per release with Watchtower on the Pi — rejected: refresh would mean rebuild, the coupling ADR-0003 rejected; (4) dist committed on every push to main — rejected: it forces dev-branch discipline (main becomes merge-only) and moves the Pi on every push, which is precisely what the Vercel dev environment is for; (5) push-synchronized pull (cron → webhook through the tunnel → Pi pulls) — rejected for now: at a weekly cadence a 30–60 min timer is effectively synchronized, and a webhook adds a moving part plus a small attack surface; documented as the upgrade path in `docs/self-hosting.md`; (6) an SSD purchase as a prerequisite — rejected: the working set is page-cache resident, so the SD card is not on the request path; an SSD remains a general box-health upgrade, not a Lusk requirement.

**Consequences:** ADR-0004's "GitHub Pages (or any static host)" default becomes "the Pi (primary) + pre-warmed Vercel (failover/dev)" — the cron's publishing behavior is unchanged, only the last hop differs; the freshness claim is unaffected (it reads payload file dates, not host uptime); `docs/architecture.md` §Automation is updated — the Pi is no longer "a possible future watchdog, never the workhorse"; it is the primary host, with the watchdog remaining a possible future role for the same box; `docs/self-hosting.md` (local, un-versioned per the docs convention) holds the operational how-to — compose file, timer, tunnel, failover drill; the "alive" promise now depends on the Pi being up, with Vercel as the recovery path — an honest trade recorded here rather than hidden; the pipeline contract, payload shape, and vintage seam are all untouched.
