# Vercel serves /data/ from the build output — a per-deploy snapshot, not the nginx live alias

ADR-0006 made Vercel the **pre-warmed failover and dev environment**: auto-built on push, "current as of the last push", routed to nothing until the Pi dies. The Pi's nginx serves the app at `/` and aliases `/data/` to the repo-root `public/data/` at *serve time* (ADR-0004's payload home) — a live alias that tracks the working tree. Vercel has no equivalent: it serves only what its build output contains, so a Vercel deploy of the app had no `/data/` at all — the loader's first fetch (`territoires.json`, non-optional) 404'd and the app rendered empty, even with the project root directory correctly set to `app`. The options were (1) move the payload into `app/public/` — rejected: it relocates ADR-0004's committed home and would force the Pi to mount the app tree rather than the repo root for the same files; (2) rewrite `/data/` to an external host — rejected: it adds a runtime dependency and makes the failover depend on something outside the deploy, the coupling ADR-0006 exists to avoid; (3) copy the payload into the build output — **chosen**.

**Decision (2026-08-04):** the Vite build copies `public/data/` (repo root) into `dist/data/` at build time (`vite.config.ts` — `copierPayloadEnBuild`), and the repo-root `vercel.json` drives the Vercel deploy end to end — `installCommand` (`npm --prefix app ci` — `ci`, never `install`, so the build cannot mutate the app manifests; the root `package.json` is a scripts-only wrapper), `buildCommand` (the same wrapper), `outputDirectory` (`app/dist`), and the SPA fallback (rewrites → `/index.html`) that nginx's `try_files` gives the Pi — with `/data/` excluded from the fallback (a passthrough rewrite first, so a missing payload file 404s and the loader's « 404 = theme absent » contract holds, instead of returning index.html and failing the JSON parse) — so the Vercel project needs no dashboard root-directory setting (leave it at the default `/`). The `/data/` URL contract is identical on both hosts; the freshness mechanics differ by design: the Pi serves the live working tree, Vercel serves a per-deploy snapshot. ADR-0003's rejection of "embed the payload in the app bundle at build time" is untouched — that reasoning governs the *app code* on the primary host (a data refresh must not mean an app rebuild); the Vercel copy is a deployment step on a host whose documented role is snapshot-at-push, and the app's own bundle never contains the data.

**Consequences:** any push to main — code or the weekly payload commit — redeploys Vercel with the current payload, so the failover stays current as advertised; the Pi's nginx alias and the "app never ships the payload" principle are unchanged; the tag-gated dist commit (`docs/self-hosting.md`) will include `dist/data/` harmlessly, shadowed by the nginx alias; local `npm run build && npm run preview` now reproduces the Vercel behavior exactly (both serve `/data/` from `dist/data/`); dependencies install fresh per deploy (no root lockfile to key Vercel's cache on — a ~5 s cost, irrelevant at failover cadence).
