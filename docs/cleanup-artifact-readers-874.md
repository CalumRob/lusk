## Résumé exécutif et limites

#868/#871 retirent les modèles de lecture des sources browser actuelles de la fiche et des Pages d'indicateur; ils ne suppriment ni les fichiers de `public/data/modeles-lecture`, ni leur copie `app/dist`, ni le routage statique. **Le built `app/dist` commis à ce commit a toujours des lecteurs effectifs** : `app/dist/assets/IndicateurView-DM4lhusy.js` contient les fetch du manifeste et du modèle indicateur; `app/dist/assets/index-DxgVtBSz.js` (ligne minifiée 238) contient le fetch modèle de territoire. Les sources et l'artefact compilé contiennent chacun **1 271 fichiers** sous cette famille (manifeste, deux modèles indicateur, modèles par territoire). `vercel.json` sert explicitement `/data/modeles-lecture/(.*)` depuis `app/dist`. Donc la coupure source n'est pas une coupure du bundle commis; il reste un consommateur compilé pertinent à tout déploiement qui servirait cette sortie. Cela ne prouve pas que le bundle est celui actuellement déployé : identité/acceptation frontend déployée inconnue.

Point d'exception important à la règle « plus de lecteur browser » : après #873, `/carte` démarre explicitement les six `indicateurs_*`, `histoires_*` et `theme_*`. C'est la décision propriétaire carte-only pour maintenir tabs/presence et consommateurs existants de métadonnées (dont rangs/presentation). Les valeurs numériques des couches API sont acquises via l'API et les lignes statiques filtrées; ce n'est pas un fallback numérique. Ne pas qualifier ces fichiers de morts en raison de la migration numérique.

Les artefacts de thème statiques ont plusieurs lecteurs distincts : source browser carte, validation/tests, consommateurs d'export/publishing, et deux chemins de construction des modèles territoriaux. Le target planifié assemble des payloads canoniques **en mémoire**; le script manuel relit au contraire les JSON publiés. Ils ne sont pas le même reader ni la même autorité d'entrée.

### Lecteurs producteur : distinction essentielle

1. **Targets planifié** — `pipeline/_targets.R` construit la target de format file `modeles_territoire`, prenant `publie_*`, `metadata_*`, `vintages_table_*` et projection Programmes en objets R déjà obtenus par graphe, puis appelle `publier_modeles_territoire_complet()`. Ce chemin ne passe pas par les JSON publiés comme inputs.
2. **Rafraîchissement manuel** — `pipeline/scripts/publish-territory-models.R` lance `publier_modeles_territoire_depuis_json()` sur le répertoire d'entrée (défaut `public/data`), qui parse les JSON nécessaires, construit les six payloads et appelle le builder complet. Cette fonction lit aussi, pour Mobilité, `profils_acces_bpe.json`, `distribution_acces_batiments.json`, `rampe_acces_batiments.json` (obligatoires dans le chemin visible), plus projections comparaisons facultatives. Ce sont des lectures réelles du helper, mais pas les inputs du target planifié.
3. **Export statique & consommateurs browser** — `publish.R` écrit payloads JSON; `CarteView` démarre son set explicite. Les tests validators/parity/R/TS assertent schémas et transformations; les assertions ne sont pas comptées comme consommateurs produit. `app/dist` est déjà construit/commis et doit être traité séparément de `app/src`; aucune suppression/rebuild effectuée.

## Conditions de retrait et follow-ups indépendants

Conditions minimales communes avant tout futur contrat/suppression (aucune action autorisée par #874) : actualiser ce graphe à la tête fusionnée; rechercher sources **et** appelants transitive/export/validators/build/static-serving; établir source, built et déployé séparément; nommer le remplacement pour chaque surface; préserver publication canonique et clocks; définir rollback/recovery; obtenir la décision propriétaire de rétention; tests de contrat sur les deux côtés; changement de retrait distinct revue séparément. Une absence de hit grep n'est pas preuve de fin de vie.

Propositions pour triage futur (pas d'issues créées ici) :

1. **HITL — reçu opérationnel nécessaire aux décisions d'artefact** : l'opérateur/propriétaire fournit un receipt non-secret et daté avec commit frontend actuellement servi et état cache/rollback, publication/version des artefacts concernés, DB marker/version si pertinent, pointeurs/générations actuellement référencés, backup/rollback candidates et règle de conservation. Cela ne nécessite pas d'accès DB par le worker. Avant le receipt, une personne doit décider quelles preuves peuvent être partagées et de la politique rétention; ce n'est pas une action AFK autonome.
2. **HITL — disposition du modèle territorial** : décider séparément du helper JSON manuel et des outputs; comparer target in-memory, `validate:territory-model`, rang fields inclus, publishing/recovery et remplacement browser. L'absence du fetch dans source n'annule pas l'actuel lecteur dist; suppression de données exige la dépendance 1 + preuve d'un nouveau bundle déployé/rollback. Le retrait isolé d'une fonction/helper source dont aucun caller/contrat ne dépend pas nécessairement de la règle DB/rétention; sa suppression peut être étudiée indépendamment, avec assertions/outils directs mis à jour.
3. **HITL — modèle indicateur / `read_model`** : décider de retirer la capacité génératrice, coordonner producer, schema validators, artifact set, tests, static serving et old built runtime. La disparition source-only ne suffit pas; outputs supprimables seulement après vérification du bundle post-cutover et des chemins de publication/recovery (dépendance 1).
4. **HITL — champs de rank fixed-scope** : le contrat de source→JSON→modèle et l'exemple d'artefact sont maintenant tracés ici. Décider par consumer/product si les champs doivent rester dans les exports statiques. Pour retirer le champ du modèle/export il faut supprimer/adapter ce chemin de publication + readers JSON/ancien bundle/tests; l'unknown actual DB/deployed generation ne bloque pas la seule étude de code mais bloque le pruning d'une génération publiée/restaurable (dépendance 1). Conserver les rangs des scopes exactes et ne jamais re-étiqueter un rank API d'un autre scope.
5. **HITL — native scalar helper field-only cleanup** : candidats déterminés ci-dessus (helpers test-only et `pathIndicator` inert) peuvent être estimés sur références source/tests; ils ne sont pas couplés automatiquement au cleanup des JSON ou à la preuve de publication DB. Avant effacement d'un helper, compiler/caller tests et toute référence du bundle généré doivent être vérifiés; aucun live-generation receipt n'est requis si aucun artefact n'est touché.
6. **HITL — acquisition carte carte-only** : proposer distinctement un remplacement des tabs/presence/theme metadata ou conserver le coût statique déjà accepté. Ne pas annuler le choix #873 dans cet audit.
