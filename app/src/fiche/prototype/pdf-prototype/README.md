# THROWAWAY — client-side Cahier PDF feasibility

Question: can an explicit A4 template consume resolved Cahier content and existing vector charts, with matching comparison context, without a PDF browser service on the Pi?

Run from `app/`: `npm run prototype:cahier-pdf`.

Requires the locally installed Playwright Chromium (`npx playwright-core install chromium` if absent). Chromium is ONLY the local automation client clicking the download. The PDF is generated by pdfmake in the browser, never `page.pdf()` or server-side Chromium. For manual use, run `npm run dev -- --port 5198` and visit `/prototype-cahier-pdf.html`.

Outputs: `E:/Temp/opencode/cahier-pdf-prototype/`, including both PDFs, per-selection JSON snapshots, screenshot, and timing receipts. This Windows path is intentional for this local experiment.

## Verdict

Feasible for the tested Mobilité chapter: four A4 sheets, explicit subject boundaries, repeated identity/chapter header and comparison footer, source provenance, zero vs unavailable distinction, vector charts and selectable text. Browser-only generation was about 200 ms on first export and 60 ms warm on this development machine (not a Pi or mobile benchmark; cold-network bundle cost not measured).

Content flows through the existing `territoryFactsFor` → `resolveMobiliteThemeContent` fixture chain. No HTML numeric parsing, live-data requests, new calculations in the exporter, or production route changes. Existing chart SVG geometry is reused, computed CSS colours flattened, and HTML tick positions copied into the SVG. A typed production figure-export seam would be preferable to these DOM selectors.

## Deliberate limits / next experiment

- SYNTHETIC existing fixtures for Commune A1, NOT a territorial report with live API facts. The legacy fixture builder computes its own fixture medians; this is not a replacement for API-backed production comparisons.
- Only “Le partage de l’espace public”, three existing bars figures. Sparse fixtures deliberately expose missing-data states. AEDAR maps, ramps, selected-member groups and all six themes remain unverified.
- Global comparison visible/hidden is the only control. Chart-local toggles are inert in the harness so captured state cannot diverge. In production every relevant local selection must be explicit in the snapshot and the assets bound to that same generation.
- An explicit PDF presentation is maintained separately from screen layout. Subject starts are intentional, not evidence that arbitrary content paginates well. Long names, tables, paragraphs, and font substitutions need further stress testing.
- Roboto bundled by pdfmake is used for PDF text, not the final Mozilla/Fira typography. Screen colours come from existing editorial/mode tokens; paper background is preserved in the file, physical print colour is not guaranteed.
- Table numeric formatting uses four significant figures to avoid displaying a small nonzero comparison as zero. Final number-format policy needs a shared app-owned choice.
- No tooltips, maps, tagged-PDF accessibility validation, mobile performance measurement, production build integration or site-wide export buttons.
- pdfmake is lazy-imported at export. Its minified JS and default VFS fonts are approximately 835 KB + 855 KB uncompressed. A production version should ship only required fonts and check compressed transfer and memory on low-end phones.

Prototype captured on branch `prototype/cahier-pdf`; no implementation issue was created because this is a feasibility artifact, not a shipping commitment.

### What the real test validated

- Five native 900×900 WebP maps can be decoded client-side into PNG for pdfmake.
  Their actual sidecar legends, including local loss-scale warnings, are retained.
- Four existing chart SVGs retain geometry, dashed comparisons, alpha, numeric
  ticks and mode colours. Their external HTML tick labels must be copied into the
  exported vector. Legends must explicitly map the colours to mode names.
- The HTML waffle becomes 235 vector tiles with counts from its existing
  resolved classification, not an independent classification algorithm.
- Scalar values, comparison values and served ranks are sourced from resolved
  content. PDF inspection confirmed 209.3 vs 165.6 types/address, rank 1/43,
  proper A4 dimensions, repeated context/page numbers and all five embedded maps.
- All 235 categories remain accounted for. Changing 15 → 10 minutes changes
  waffle counts from 111/44/38/12/10/20 to 77/19/57/37/17/28 in the renderer's
  existing bucket order. The selected B207 distribution also follows 10 minutes.
- Existing car/loss maps remain explicitly 15-minute maps even when the
  equipment horizon changes; a report-wide blanket horizon would be false.

### Limits exposed (not production-ready)

- `rennes.js` reaches into Vue **development internals** to capture resolved
  component props/computeds. This avoids parsing factual HTML but is deliberately
  brittle. Production needs an explicit typed export-state seam that includes
  the child-owned equipment detail/comparison and effective local selections.
- Parent `aedarSelectedHorizon` is initially null while child figures really
  show 15 minutes. The first experiment caught a `null minutes` footer; final
  exports instead capture each child's effective horizon and verify it.
- The snapshot, chart geometry, colours and selected modes are frozen before
  asynchronous image conversion/import. Production still needs generation/coherence
  guards for failures, late responses and user changes during preparation.
- PNG maps dominate file size and conversion cost. Native map detail, compressed
  transfer, low-end phone time/memory, and optional image downsampling need a
  separate measurement. No Chromium memory burden is introduced on the Pi.
- Eight sheets is a deliberately generous semantic template, not optimized
  editorial pagination. A first map layout stranded interpretation prose on a
  continuation page; moving that commentary intact to the source/method page
  removed the orphan. No paper-height clipping or silent truncation is used.
- Typography remains Roboto; screen typography and accessible PDF tagging are
  unvalidated. Closed dialogs/tooltips and full equipment tables are not exported.
- Existing source prose is preserved verbatim, including screen-only interaction
  instructions and an overview sentence saying aggregate ranking is unavailable
  although current scalar evidence supplies ranks. Those are content issues to
  resolve explicitly, not facts for the PDF adapter to silently rewrite.

Verdict: the real map-heavy chapter is feasible with browser-only pdfmake. The
next engineering problem is an explicit, coherent export-state/figure interface,
followed by a real A4 editorial pass and low-end-device performance checks—not a
generic HTML-to-PDF parser or a Pi-hosted browser service.

## Desktop-fidelity / selectable-text revision

Run `npm run prototype:desktop-pdf` from `app/`. Local prerequisites: the
Playwright Chromium and Python `fonttools` + `brotli`. Outputs live under
`E:/Temp/opencode/cahier-desktop-pdf/`, especially `rennes-desktop-epci.pdf`.

This revision **does not use the preceding PDF chapter template**. A deliberately
narrow DOM paint adapter uses the browser's existing desktop layout, computed
colours, glyph positions, SVGs, images and source annotations. It creates real PDF
text and vector paths with jsPDF/svg2pdf; it does not use a screenshot or an
invisible text layer over a screenshot. The five source maps remain raster maps.

Header: the site's actual ermine/wordmark; the Cahier's actual heading in the
centre; territory name and the existing Contact external-link icon on the right.
The right-hand link targets the public territory URL with its comparison query.
The rule's colour/style comes from the existing sticky Cahier heading. The
footer retains the resolved comparison label and physical PDF page numbering.

The font helper derives static TTF faces from the installed site's own Fontsource
WOFF2 files, using observed family/weight/style values rather than a font-family
map. Generated fonts are local, ignored, and regenerated by the command; do not
commit them or deploy this prototype's public directory. The helper clamps
variable axes to their declared ranges and produces a synthetic oblique when the
site requests italics from a family without an italic face. PDF tagging, synthetic
bold, non-Latin shaping and arbitrary font features remain unvalidated.

Only selected toggle/horizon states remain in the capture. Tooltips, unused
actions and section exploration footers are excluded. The waffle uses the actual
DOM tile positions, not a reconstructed fixed-column grid. Sources retain their
actual inline placement and links; no extra source appendix is invented.

Pagination measures whole sections and desktop gaps, packs adjacent sections
when they fit, and vertically centres the resulting group on each sheet. A
single uniform scale preserves relative proportions throughout the document.
The width-derived scale is reduced only if the largest whole section would
otherwise exceed the printable height. Nothing is silently split or clipped.
Rennes currently gives four sheets: intro + car overview; loss maps; time ramps
+ classification; equipment explorer. Exact desktop proportions mean some
physical A4 labels are small (roughly 5–8 pt). This is a real readability trade-off,
not a claim that the A4 design is finished.

The tested revision is roughly 1.7 MB and takes about 2.5 seconds to export on the
development machine. This excludes initial live-page loading and font generation;
it is not a phone/Pi benchmark. No PDF browser service runs on the Pi.

### Maintenance boundary

Copy, factual values, colours, fonts, tile positions, source placement and section
geometry are read from the actual rendered site, not duplicated per section.
Paper margins, packing/centring and the requested header composition remain
PDF-owned presentation. **This is not a complete browser renderer:** unsupported
CSS, pseudo-elements, complex clipping, effects, scripts or text shaping can still
need adapter work. Vue dev internals are still used only for readiness/context.
New site design features must be verified; automatic perfect fidelity for every
future CSS change is not promised. The untouched live site is not modified by
capture: pruning occurs in an off-screen DOM clone, removed in `finally`.

### Legend/brand/footer corrections

The legend defect was in the adapter: it parsed the first radius of a CSS
four-corner value as a uniform radius, creating gaps between swatches, and drew
CSS dashed borders as solid lines. `paintGeometry.js` now preserves all four
elliptical corner radii and border dash patterns. Regressions run offline with
`node --test scripts/prototype-desktop-paint.test.mjs`.

The wordmark defect was font selection, not the brand component: the helper
chose the package's true italic Newsreader face, but the site imports only its
normal face and synthesizes italics. Font generation now consults the actual
loaded browser faces before selecting its source. The manifest records source
provenance so this can be checked without guessing from a family name.

The cloned brand links home. A clickable superscript `¹` beside both legend and
scalar comparison labels jumps to the matching context on that sheet's footer.
The footer also contains a small linked invitation to visit the site. URLs derive
from the existing public-page URL, not duplicated territory identities.

After generating the PDF, run `python scripts/verify-prototype-desktop-pdf.py`
from `app/` (local PyMuPDF needed). It checks the real artifact's font provenance,
header/homepage/CTA URLs, internal footnote destinations, dashed legend paths,
page dimensions and retained text/vector output.
