# THROWAWAY — client-side Cahier PDF feasibility

Question: can an explicit A4 template consume resolved Cahier content and existing vector charts, with matching comparison context, without a PDF browser service on the Pi?

Run from `app/`: `npm run prototype:cahier-pdf`.

Requires the locally installed Playwright Chromium (`npx playwright-core install chromium` if absent). Chromium is ONLY the local automation client clicking the download. The PDF is generated by pdfmake in the browser, never `page.pdf()` or server-side Chromium. For manual use, run `npm run dev -- --port 5198` and visit `/prototype-cahier-pdf.html`.

Outputs: `E:/Temp/opencode/cahier-pdf-prototype/`, including both PDFs, per-selection JSON snapshots, screenshot, and timing receipts. This Windows path is intentional for this local experiment.

## Verdict

Feasible for the tested Mobilité chapter: four A4 sheets, explicit subject boundaries, repeated identity/chapter header and comparison footer, source provenance, zero vs unavailable distinction, vector charts and selectable text. Browser-only generation was about 200 ms on first export and 60 ms warm on this development machine (not a Pi or mobile benchmark; cold-network bundle cost not measured).

Content flows through the existing `territoryFactsFor` → `resolveMobiliteThemeContent` fixture chain. No HTML numeric parsing, live-data requests, new calculations in the exporter, or production route changes. Existing chart SVG geometry is reused, computed CSS colours flattened, and HTML tick positions copied into the SVG. A typed production figure-export seam would be preferable to these DOM selectors.

## Deliberate limits / next experiment

- SYNTHETIC existing fixtures for Commune A1, NOT a territorial report with live API facts. The legacy fixture builder computes its own fixture medians; this is not a replacement for API-backed production comparisons.
- Only “Le partage de l’espace public”, three existing bars figures. Sparse fixtures deliberately expose missing-data states. AEDAR maps, ramps, selected-member groups and all six themes remain unverified.
- Global comparison visible/hidden is the only control. Chart-local toggles are inert in the harness so captured state cannot diverge. In production every relevant local selection must be explicit in the snapshot and the assets bound to that same generation.
- An explicit PDF presentation is maintained separately from screen layout. Subject starts are intentional, not evidence that arbitrary content paginates well. Long names, tables, paragraphs, and font substitutions need further stress testing.
- Roboto bundled by pdfmake is used for PDF text, not the final Mozilla/Fira typography. Screen colours come from existing editorial/mode tokens; paper background is preserved in the file, physical print colour is not guaranteed.
- Table numeric formatting uses four significant figures to avoid displaying a small nonzero comparison as zero. Final number-format policy needs a shared app-owned choice.
- No tooltips, maps, tagged-PDF accessibility validation, mobile performance measurement, production build integration or site-wide export buttons.
- pdfmake is lazy-imported at export. Its minified JS and default VFS fonts are approximately 835 KB + 855 KB uncompressed. A production version should ship only required fonts and check compressed transfer and memory on low-end phones.

Prototype captured on branch `prototype/cahier-pdf`; no implementation issue was created because this is a feasibility artifact, not a shipping commitment.
